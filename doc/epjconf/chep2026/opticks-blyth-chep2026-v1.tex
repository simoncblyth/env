\section{Introduction}%
\label{intro}
%
Opticks~\cite{opticks,chep2024,chep2023,chep2021,chep2019,chep2018,chep2016} applies NVIDIA\textregistered\ OptiX\texttrademark~\cite{optix} GPU ray tracing, including RT Core 
hardware acceleration on NVIDIA RTX GPUs~\cite{rtx}, to optical photon simulation and integrates this with Geant4~\cite{g4} for all other particles.
Offloading optical photon simulation to the GPU eliminates processing time and memory bottlenecks especially for
large high-yield detectors such as the 20 kton Jiangmen Underground Neutrino Observatory (JUNO)~\cite{juno}. 
Although developed for JUNO, Opticks has been used by other experiments including LZ~\cite{lz}, NEXT~\cite{next}, DUNE~\cite{dune}
and the Electron Ion Collider~\cite{eic}. Prior CHEP proceedings~\cite{chep2024,chep2023,chep2021,chep2019,chep2018,chep2016} cover the development history of Opticks.
These proceedings focus on enhancements motivatated by JUNO production experience with high energy events, such as cosmic-ray muons which can yield several billions
of optical photons per event.
%
%
\newpage
\subsection{Opticks solution to the optical photon simulation problem}
Simulating optical photons resulting from cosmic ray muons crossing the JUNO liquid scintillator consumes
more than 99.5\% of total CPU time in standard Geant4~\cite{g4} based simulations. The execution time is dominated by 
ray tracing, calculating intersection positions of rays representing photon steps with the detector geometry,

Optical photon simulation is exceptionally well suited to GPU parallelization, due to
the natural massive parallelism of billions of independent photons and the simplicity of optical physics
requiring minimal register memory per thread.
NVIDIA OptiX~\cite{optix} provides a single-ray programming model that 
leverages state-of-the-art acceleration structures and dedicated RT Cores on NVIDIA RTX~\cite{rtx} GPUs.
This has enabled Opticks to execute the entire photon simulation lifecycle from generation through to
absorption or detection entirely within a single GPU kernel launch.
Optical material and surface property lookups are highly optimized on the GPU using hardware-accelerated texture lookups 
with wavelength interpolation.
%
%

\subsection{Hybrid CPU+GPU Simulation Workflow}
%
\label{secworkflow}%
%
%
\begin{figure}[htb]
\centering
%                                    left lower right upper
\includegraphics[width=\textwidth,trim={0 4cm 0 4cm},clip]{env/Documents/Geant4OpticksWorkflow7/Geant4OpticksWorkflow7_005.png}
\caption{This figure is reproduced from~\cite{chep2023}, which provides further details. Illustration of the
hybrid Geant4 + Opticks workflow : {\tt G4CXOpticks} translates Geant4 geometry to GPU appropriate form. 
{\tt U4} collects "gensteps" enabling GPU generation of scintillation and Cerenkov photons. 
}
\label{figworkflow} 
\vspace{-5mm}
\end{figure}
%
%
Figure~\ref{figworkflow} illustrates the Opticks geometry and event simulation
workflow. During initialization, the Geant4 optical material and surface properties are uploaded to GPU textures
and the volume tree and solids are translated into an NVIDIA OptiX geometry, using an analytic CSG representation
of most solids and optionally a triangulated representation of some solids such as the JUNO guide tube torus.

Rather than generating individual optical photon tracks on the CPU within
Geant4 scintillation and Cherenkov process loops, Opticks collects process
parameters into compact "genstep" arrays. These genstep arrays are uploaded to
the GPU, where an OptiX ray-generation program generates and propagates the
corresponding photons in parallel using one CUDA thread per photon.

Opticks conceptually propagates all photons simultaneously, however the
maximum batch size per CUDA launch is bounded by the VRAM allocated for photon
state arrays. During initialization, Opticks queries the total available VRAM
and heuristically computes the maximum photon capacity per launch. For each
event, the genstep array is sliced into a vector of launch batches to ensure
photon device allocations remain within available VRAM limits.

\subsection{Optical Photon Simulation Implemented within OptiX Ray Generation Program}
\label{sec:kernel}
\begin{samepage}
%
Listing~\ref{lst:propagatekernel} is a summary of the NVIDIA OptiX ray generation program
that implements the full simulation of a single optical photon from generation through
to absorption or detection. Scintillator reemission is treated as "rebirth" 
of the photon within the same single thread. Each optical photon thread has a unique {\tt photonIdx}
allowing all threads to simultaneously write into photon arrays.
%The seed array gives access for each photon to the associated parent genstep parameters.
%
The trace call at each while loop iteration
finds the intersection of a ray with the current photon position and momentum direction
with the detector geometry. The prd struct includes the distance to the intersection 
and the surface normal at intersection. The {\tt qsim::propagate} call implements
scattering, reemission, boundary physics, surface effects, absorption and detection.  
Optionally the final photon can be persisted into device global memory using
arrays of 64(16) byte {\tt sphoton(sphotonlite)} struct.
Also a "record" array can persist the photon history at up to maxRecord steps enabling
detailed debugging and animated photon history visualizations.   
%
\begin{lstlisting}[numbers=none, caption={Optical photon simulation implemented within NVIDIA OptiX ray generation program.}, label={lst:propagatekernel}]
sevent* evt = params.evt ;
unsigned genstepIdx = evt->seed[photonIdx] ;
const quad6& gs = evt->genstep[genstepIdx] ;

qsim* sim = params.sim ;

RNG rng ; // random number generation state 
sim->rng->init( rng, evt->index, photonIdx );

sphoton p ;
sim->generatePhoton(p, rng, gs, photonIdx, genstepIdx );

quad2 prd ; // per-ray-data

int command = START ;
int bounce = 0 ; 
while( bounce < params.maxBounce && p.time < params.maxTime )
{   
    trace(params.geom, p.pos, p.mom, params.tmin, params.tmax, prd );
    command = sim->propagate(bounce, rng, p);

    if(evt->record && bounce < evt->maxRecord) 
        evt->record[evt->maxRecord*photonIdx+bounce] = p ;

    bounce++;
    if(command == BREAK) break ; // photon absorbed or detected
}   

if( evt->photon ) evt->photon[photonIdx] = p ;   // final photon
if( evt->photonlite )
{   
    sphotonlite l ;
    sphotonlite::summarizePhoton(l, p) ; 
    evt->photonlite[photonIdx] = l ;
}   
\end{lstlisting}
\end{samepage}

\subsection{Opticks Event Arrays and Simulation Workflow}
%
The main event arrays utilized during optical photon simulation are detailed in Table~\ref{tabeventarrays}. 
Prior to launching the simulation kernel, the genstep array collected from Geant4 is transferred to the GPU. 
A seed array is then constructed on the device by expanding the genstep photon counts into parent genstep indices 
using CUDA Thrust~\cite{thrust} parallel primitives (\texttt{sysrap/iexpand.h}). 
This seed array allows each parallel CUDA thread to look up its corresponding parent genstep parameters 
and generate the initial photon state on the device.

The simulation kernel, described in Section~\ref{sec:kernel}, typically populates the full 64-byte \texttt{photon} array 
or the reduced 16-byte \texttt{photonlite} array with final state data upon absorption or detection. 
For detailed validation, the kernel can optionally record the complete step history in the \texttt{record} array 
and store a step-by-step history of 4-bit flag sequences in the \texttt{seq} array.
%
Following optical transport, hit creation kernels extract the subset of detected photons directly on the device 
to populate the \texttt{hit}, \texttt{hitmerged}, \texttt{hitlite}, or \texttt{hitlitemerged} arrays (Section~\ref{sec:hitmerge}). 
All event arrays can be downloaded and saved as NumPy binary files for Python analysis.
%

\section{Simulation of High-Energy Events and Hit Merging}
%
High-energy events such as multi-muon cosmic-ray bundles traversing long path lengths in the JUNO
liquid scintillator, as depicted in Figure~\ref{figmultimuon}, can generate billions of optical photons.
Recording details for every photon detected by PMTs 
in such events generates gigabytes of hit data, exceeding requirements of typical physics analyses. 
To address this, the simulation offers configurable summary hit collection. 
Aggregating hits arriving at the same PMT within configurable time windows into a single merged hit
with the total photon count and earliest hit time allows data storage requirements to be drastically reduced.

In the standard CPU-based JUNO simulation, hit merging is implemented using per-PMT hit collections. 
For the standard simulation the merge overhead is negligible compared to photon propagation time.
%
Initially, the Opticks-JUNO workflow reused this CPU hit-merging algorithm 
by downloading all unmerged photon hits from GPU memory prior to merging.
However, after accelerating the photon transport the
CPU-side hit merging became the dominant computational bottleneck for optical photon processing. 
This limitation motivated the development of on-device GPU hit merging using CUDA Thrust 
and a compact summary data structure (\texttt{sphotonlite}), enabling Opticks to minimize 
VRAM usage, cut memory transfer overheads, and avoid post-processing from hiding the benefits of GPU acceleration.
%
%
\subsection{CUDA Thrust Implementations of GPU Hit Selection and Merging}
\label{sec:hitmerge}
%
%When GPU hit merging is not configured the hit arrays (\textt{hit} or \texttt{hitlite}) are
%filtered from 
%selected from the \textphoton(photonlite) arrays with a device to device copy based on photon flag mask indicating detection 
%using CUDA Thrust stream compaction via {\tt thrust::copy\_if}.
%
%
When hit merging is enabled, the merged hit arrays (\texttt{hitmerged} or
\texttt{hitlitemerged}) are filtered and aggregated directly from their parent
arrays (\texttt{photon} or \texttt{photonlite}) using a single CUDA Thrust
method, \texttt{SPM::merge\_partial\_select}. This single-pass approach
eliminates the need for intermediate memory allocations or separate processing
phases.  Because hit selection and merging apply to both 64-byte
(\texttt{sphoton}) and 16-byte (\texttt{sphotonlite}) structures, templated
functor implementations specialize the selection, sorting, and reduction.
For example, the crucial \texttt{key\_functor} packs the PMT identifier and time
bucket index into a 64-bit key, uniquely identifying hits onto a PMT within 
the same time window.

For events where available VRAM allows simulating all photons in a single launch, a single execution
yields the configured hit array. For larger events requiring multi-launch execution, 
partial hit arrays are merged after each launch batch, concatenated on the CPU, and re-uploaded to the GPU for a final, 
unfiltered merge pass.

Table~\ref{tab:opticks_junosw_performance} compares performance across four
output hit modes. Because ray-tracing propagation is identical across all
cases, the GPU kernel execution time remains constant at $\sim$23\,s. 
Performing hit merging on the GPU yields a dual benefit: it eliminates the
CPU hit-merging bottleneck and reduces host-device transfer
volume by roughly $4\times$ due to hit reduction. 

The 6.3-second timing difference between \texttt{hitmerged} and
\texttt{hitlitemerged} modes is dominated by local coordinate transformation.
For full \texttt{sphoton} hits, local PMT frame transformations ($4\times4$
matrix operations) are currently performed on the CPU during hit collection.
For \texttt{sphotonlite} hits, coordinate transformation is calculated on the
GPU during the simulation kernel. Offloading remaining local transformations to
the GPU is expected to close this gap.

In these single-launch benchmarks (150M photons), the full capacity advantages
of \texttt{sphotonlite} are masked because total memory stayed within 32\,GB
VRAM limits. On this hardware, maximum single-launch capacity is approximately
250M full photons versus 500M lite photons—a $2\times$ gain rather than the
theoretical $4\times$ struct size ratio due to transient workspace allocations
required by CUDA Thrust during sorting and reduction. When summary photon information
is sufficient using \texttt{sphotonlite} effectively doubles the usable event capacity of the available
GPU VRAM.
%

As a stress test of multi-launch simulation an artificial event with 8.25 billion optical photons
was simulated with full merged hits in 33 launches using 32\,GB VRAM.

\section{Scaling Opticks for Monte Carlo Production}

Opticks eliminates the optical photon bottleneck in Geant4 simulations;
however, sustaining high GPU resource utilization across production Monte Carlo campaigns 
with diverse workloads and hardware capabilities remains challenging.
Optical simulation performance has roughly doubled with each NVIDIA RTX GPU generation 
due to ray-tracing hardware advances, making GPU starvation an increasingly critical issue.
In a monolithic Opticks application, the GPU remains idle during Geant4 initialization 
and non-optical simulation phases. 
While overlapping CPU work with GPU propagation is expected to yield moderate gains, adoption of
a client-server architecture offers the architectural flexibility to fully saturate GPU resources,
eliminate redundant geometry initialization costs, and mitigate GPU hardware scarcity. 
Crucially, tuning the ratio of CPU clients to GPU servers in production campaigns affords fine-grained 
control over GPU utilization, decoupled from specific workloads or the evolving hardware capabilities.

The multi-package structure of Opticks organized by dependency has enabled a
straightforward division with client and server components compiled from a single codebase.
Core optical simulation packages requiring CUDA and OptiX
are isolated on the remote server, which services requests from lightweight clients. 
The current prototype server uses Python, FastAPI, and nanobind to expose the C++ \texttt{CSGOptiX} simulation engine, 
with the client relying on \texttt{libcurl} to provide HTTP transport.


\section{Summary and Outlook}

Production experience with the simulation of JUNO high energy events
have motivated development of a reduced resource simulation mode and GPU hit merging
that avoid the benefits of Opticks accelerated optical photon simulation from being
obscured by CPU post processing.

Prototyping the FastAPI-based Opticks server has been instructive. However,
adopting the NVIDIA Triton Inference Server with Opticks as a custom backend
is expected to offer a more production-ready foundation suitable for achieving
the robust multi-client throughput required for large-scale Monte Carlo production.

Shader Execution Reordering (SER)~\cite{ser} is an optimization technique introduced with the Ada 
generation of RTX GPUs that reduces execution and data divergence in ray tracing kernels by on-the-fly reordering of threads that
are performing similar work resulting in improved GPU utilization.
%This functionality is supported from NVIDIA OptiX 8, with the \texttt{optixReorder} call. 
Studies using the Simphony~\cite{simphony} Opticks fork report~\cite{sergalgoczi} an order of magnitude reduction
in optical kernel execution times with a 1.4kt Liquid Argon Time Projection Chamber geometry. 
Reductions in optical kernel duration from SER and future RTX generations will likely be particularly beneficial in the
context of an Opticks GPU server where the processing bottleneck has been shifted from CPU to GPU. Future work will measure both optical
and overall application speedups provided by SER for high-energy event simulations within the JUNO detector geometry.

Current distributed computing frameworks like DIRAC, HTCondor and Slurm 
lack the fine-grained matchmaking capabilities necessary to detect and route jobs
based on preference for specific GPU microarchitectural features such as RT cores
or Shader Execution Reordering (SER)~\cite{ser}. Future work will address this lack in the context
of scaling up the Opticks enhanced JUNO simulation.
